# any — the embeddable `any` backend artifact

`any` is the versioned, per-platform artifact the **Any** desktop app
(`anyproto/any-ui`) embeds; the same release carries the mobile bindings.
CI builds it on tag (release) and nightly (prerelease), publishes one GitHub
Release, and fires a `repository_dispatch` that notifies the client repos
(`any-ui` desktop, `anytype-swift`, `any-kotlin`) to kick their own builds.
Build one desktop payload locally with `make any` (or `scripts/build-any.sh`).

## Tarball layout (`any-<version>-<os>-<arch>.tar.gz`)

- `any[.exe]` — the backend (built from `cmd/any` with `-tags llamacpp`,
  which adds the local embedder — `docs/13-index.md` § Builds and the
  local embedder).
- `llamacpp/` — prebuilt llama.cpp shared libs for this `(os,arch)`
  (`scripts/fetch-llamacpp.sh`). The local embedder loads them from
  `index.local.libDir`, else `$YZMA_LIB`, else `<dir-of-any-exe>/llamacpp`.
- `LICENSE` — Any's MIT license and copyright notice, copied from the repository.
- `manifest.json` — `{ version, os, arch, llamacpp_version, sha256: {path: hash} }`.
  Consumers verify every file against `sha256` before use.

`<arch>` is `arm64` or `x86_64` (the `darwin-x64` platform ships as
`darwin-x86_64`).

The default embedding model (`Qwen3-Embedding-0.6B-Q8_0.gguf`) is **not**
bundled — it downloads at runtime into `<data-dir>/models/`.

The darwin tarballs are any-ui's sidecar; any-ui carries the
`disable-library-validation` entitlement and signs the sidecar itself.

## Platforms

Published desktop platforms: `darwin-arm64`, `darwin-x64`, `linux-x86_64`,
`windows-x86_64`. The backend is CGO-free (purego `dlopen`), so one
Linux job cross-builds every desktop target and cross-fetches each platform's
libs.

Mobile: `any.aar` (Android, arm64-v8a only, `make build-android`) and
`any.xcframework.zip` (iOS device + simulator, `scripts/build-xcframework.sh`).

## Build and publish

`release-any.yml` (on `v*` tags, channel `release`) and `nightly-any.yml`
(daily cron + manual, channel `prerelease`) both call the reusable
`_build-any.yml`:

| Job | Runner | Does |
|-----|--------|------|
| `version` | ubuntu-latest | resolves the one version every artifact stamps: the pushed tag, or `v<latest release, patch + 1>-nightly.<YYYYMMDD>.<n>` |
| `desktop` | ubuntu-latest | `make catalog-validate`, then `build-any.sh` for the four desktop platforms |
| `android` | ubuntu-latest | installs NDK `30.0.16248370` with `sdkmanager` (never the image's copy), then `make build-android` with the version as make command-line vars |
| `ios` | macos-15 | Xcode with the iOS 26 SDK, the `mobile/ios` and `mobile/android` shim tests, `build-xcframework.sh` (minimum iOS 18.4, set in `scripts/build-xcframework.sh`) |
| `publish` | ubuntu-latest | runs when at least one platform passed; verifies every asset of the platforms that built against the digest its leg wrote beside it (fail-closed), ships them with one `SHA256SUMS` manifest in one `gh release create`, the notes opening with `> **Partial release** — missing: …` when any is absent; then `any-published` to each client whose platform shipped (`scripts/release-fanin.sh`) |
| `notify-failed` | ubuntu-latest | after `publish`, unless the run was cancelled: `any-build-failed` (`version`, `channel`, `platform`, `failed_platforms`, `run_url`) to every client that got no `any-published` — a red leg, a red `version`, or a `publish` that failed (even after the release was created: nobody was told to build it) |

Every build leg hashes what it built and ships `<asset>.sha256` beside the
artifact; `publish` verifies each asset against that digest on download and
aggregates the lines into the `SHA256SUMS` release asset, which a client checks
with `sha256sum -c SHA256SUMS`. The release notes render that manifest — every
asset that shipped with its sha256 — and the llama.cpp pin, so a client can
pin without downloading first; a platform that
did not build reads `not built` under its heading, and the first line names it
as missing. Every `any-published` carries `version` and `channel`; the
`anytype-swift` and `any-kotlin` dispatches add the asset name and its sha256.
A client is dispatched only when its own asset is on the release; otherwise it
receives `any-build-failed` from `notify-failed`. Two silences remain: a
cancelled run (superseded by the newer one, which sends its own events) and an
unset `ANY_CI_TOKEN` (both directions warn and skip). The decisions live in
`scripts/release-fanin.sh`, tested by `make test`. Contract: any-ui
`docs/specs/2026-10-10-any-nightly-per-platform-publish.md`.

## Required CI secret

`ANY_CI_TOKEN` — a classic repo PAT with read+write across the `anyproto`
org. It does two jobs: (1) every build job fetches the private Go modules
(`any-sync-sdk`, …) with it via the `go-private-auth` action, and (2) the
`publish` job fires the `repository_dispatch` to the client repos (`any-ui`,
`anytype-swift`, `any-kotlin`). Store it in this repo's Actions secrets
(`gh secret set ANY_CI_TOKEN --repo anyproto/any`). The built-in
`GITHUB_TOKEN` can neither read other private `anyproto` repos nor dispatch
across repos, hence a dedicated token. Without it a build fails at module
fetch; the client dispatch is best-effort, so a missing/failed dispatch
warns but never fails the already-published release.

## PR checks

`pr-checks.yml` runs three jobs on every pull request.

`swagger-drift`:

- **swagger drift** — regenerates the OpenAPI spec (`make swagger`) and
  fails if `internal/server/docs` differs from what's committed. The spec
  is a published contract (anybao's `anyrt drift` pins against it). Fix:
  `make swagger`, commit the diff (`make build` runs the regen too). The
  spec captures routes, shapes and status codes — not the `error.code`
  strings from `docs/06-errors.md`; a code-only change is invisible to it
  and must be caught in review. `.swaggo` at the repo root is a build
  input the regen reads (passed explicitly, so a missing file fails
  `make swagger`): it describes `json.RawMessage` as an object, so
  descriptors (`xFormat`, part `ui`, type `layout`), raw records and
  record arrays keep their real shape instead of swag's `[]integer`. The
  drift gate only proves the spec matches the annotations — that the
  shapes are right is `TestSwaggerShapes` (`internal/api`).
- **go vet** over the whole module.
- **dependency guard** — `make check-deps` fails if the untagged build or
  a mobile build links the llama.cpp ffi bindings, which panic at process
  start without libffi (`docs/13-index.md` § Builds and the local
  embedder).
- **catalog validation** — `make catalog-validate` compiles the
  embedded usecase catalog (`internal/catalog/catalog.yml`) through the
  server's own gate: ids and handles, the `requires` graph (resolvable,
  acyclic), relation links, module rules, every property descriptor
  against its kind, `miniapp` values against the built-in collection —
  one `<source>: <path>: <code>: <message>` line per problem, every problem
  at once. The release workflow runs the same step in its `desktop` job,
  which `publish` depends on, so a broken catalog can neither merge nor
  ship (`docs/28-well-known-bundles.md` § Validation).

`tests` — `make test`: the shell self-tests for the release scripts
(`make test-scripts`, today `scripts/release-fanin.test.sh`), then
`go test ./...` (the `go install` build), then the packages with
local-embedder code again under `-tags llamacpp`. Network-backed
tests self-skip without a staging config.

`docs` — `make docs-check` renders the website, runs renderer vet/tests,
checks generated links, assets, fragments and search targets, and exercises
the downloadable JavaScript and Python clients with mocked HTTP responses
and streams. It uses Go, Node.js and Python; no Any server is started.

All three jobs use `ANY_CI_TOKEN` (above) for the private-module fetch, so they run
on same-repo branches, not forks.

## Windows

`windows-any.yml` is the only workflow that builds and runs a Windows binary:
on push to `main`, daily at 00:00 UTC (before the nightly publishes) and on
demand. It runs `go build -tags llamacpp ./...`, fetches the Windows
llama.cpp release the tarball ships, and runs the `internal/server`,
`internal/config`, `internal/indexer`, `internal/cli`, `internal/client` and
`internal/push` tests on `windows-latest` — including a real llama.cpp load
(`ANY_TEST_LLAMACPP_LIBDIR`), since a DLL that cannot resolve its imports
fails only at load time. It is not a PR gate.
